## 0. 新手包：checkpoint、参数名与"按名搬家"

**checkpoint 是什么**：一堆 `.safetensors` 文件，每条记录就是一个 `(名字, 张量)` 对，例如：

```
"model.layers.12.self_attn.kv_b_proj.weight"  →  shape [32768, 512] 的张量
```

**加载的本质是"按名字搬家"**：内存里已建好的模型有一套参数名（`named_parameters()` 打印的就是），硬盘上的 checkpoint 用的是另一套（可能不同）名字。加载代码的职责 = 建立两套名字的对应关系 + 处理切分/改名/变形。

三行 Python 看到自己模型的"户口本"：

```python
model = AscendGlm5NextForCausalLM(vllm_config=..., prefix="")
for name, p in model.named_parameters():
    print(name, tuple(p.shape))      # 逐行打印参数名和形状
```

**为什么这课重要**：适配一个新模型 80% 的报错都出在权重加载（名字对不上、形状不对、TP 切分错位）。看懂本课的映射表结构，你就掌握了任何 vLLM 模型适配的通用套路。

## 1. 注册：名字怎么被引擎找到

`vllm_ascend/models/__init__.py`（25 行）：

```python
ModelRegistry.register_model("Glm5NextForCausalLM",
```

checkpoint 的 `config.json` 里 `architectures: ["Glm5NextForConditionalGeneration"]` → vLLM 查注册表 → 找到我们的类。**多模态  7 课的 `init_vllm_registered_model(architectures=["Glm5NextForCausalLM"])` 也查这张表**。NPU 插件用"上游架构名 → 本地实现"的注册抢占上游默认实现。

## 2. 两张映射表（[:109-132](../glm5_next.py#L109-L132)）

### 2.1 `GLM5_TRANSFORMERS_INTERNAL_WEIGHTS_MAPPER`

```python
WeightsMapper(orig_to_new_substr={
    ".self_attn.forget_gate.A_log":  ".self_attn.A_log",      # KDA 遗忘门
    ".self_attn.forget_gate.dt_bias": ".self_attn.dt_bias",
    ".attn_hc.fn":    ".hc_attn_fn",    # MHC 混合矩阵：transformers 命名 → 我们的命名

    ".attn_hc.scale": ".hc_attn_scale",
    ".ffn_hc.fn":     ".hc_ffn_fn", ...

```

同一份权重在 HF transformers 内部实现和 vLLM 实现里的**模块命名不同**，mapper 做子串级改名。它是 `hf_to_vllm_mapper` 类属性，`AutoWeightsLoader` 消费。

### 2.2 `GLM5_PACKED_MODULES_MAPPING`

```python
{"gate_up_proj": ["gate_proj", "up_proj"],          # FFN 两矩阵合一
 "fused_qkv_a_proj": ["q_a_proj", "kv_a_proj_with_mqa"],   # MLA A 投影合一（第 3 课）

```

告诉 AutoWeightsLoader："这两个 checkpoint 权重属于同一个打包后的参数"——按 shard 分片写入（  3 课的 1536|512 拼列）。

## 3. MTP 权重的隔离（[:2519-2526](../glm5_next.py#L2519-L2526) + [:135-145](../glm5_next.py#L135-L145)）

```python
# ForCausalLM.load_weights
skip_prefixes = [MTP_ROT_WEIGHT_NAME]      # "rot.weight"
if tie_word_embeddings: skip_prefixes.append("lm_head.")
loader = AutoWeightsLoader(self, skip_prefixes=skip_prefixes)

# get_spec_layer_idx_from_weight_name（:135）
first_mtp = num_hidden_layers               # 45
if weight_name == "rot.weight" or f"layers.{>=45}." in name: return 层号
```

主模型加载时跳过一切 MTP 权重（`Model.load_weights` 里 [:2346](../glm5_next.py#L2346) 显式 continue）；MTP 模型加载时（  8 课）只接受这些权重。**同一个 checkpoint 文件流被两个模型类各取所需**——这就是投机解码权重分发的全部秘密。

## 4. Model.load_weights 的四段映射流水线（[:2321-2434](../glm5_next.py#L2321-L2434)）

多模态/文本模型中 AutoWeightsLoader 会下钻调用 `AscendGlm5NextModel.load_weights`（子模块自定义加载优先）。逐权重处理顺序：

1. **过滤**：MTP 权重、rotary_emb.inv_freq/cos_cached/sin_cached（旋转缓存不落盘加载）
2. **conv1d 特判**（[:2352-2363](../glm5_next.py#L2352-L2363)）：checkpoint 存一个 `[3*8192, kernel]` 大卷积（QKV 合写），squeeze + chunk(3) 拆成 q/k/v 三份分别写
3. **A_log 变形**（[:2364](../glm5_next.py#L2364)）：一维 → `view(1,1,-1,1)` 匹配 NPU kernel 的 4 维布局
4. **`_pad_nope_kv_a_weight`**（[:2366](../glm5_next.py#L2366)，  3 课讲过）：nope 模型补零行
5. **stacked_params_mapping**：gate_proj/up_proj → gate_up_proj shard 0/1
6. **mla_params_mapping**：q_a_proj/kv_a_proj_with_mqa → fused_qkv_a_proj shard 0/1；**wk/weights_proj → wk_weights_proj**（  4 课 Indexer 的 Merged 矩阵）
7. **expert_params_mapping**：FusedMoE 生成的 288×3 条映射（`fused_moe_make_expert_params_mapping`），带 expert_id 调 `weight_loader`
8. **兜底**：`params_dict` 里有就直接写（bias 缺失跳过、PP 缺层跳过）

每一步 `weight_loader(param, loaded_weight, shard_id)` 都是参数自带的加载函数——TP 切分逻辑封装在 vLLM 的 parallel linear 层里，模型代码只负责"指路"。

## 5. 三个设计模式总结（学了就能带走的）

1. **声明式映射 + 兜底**：能枚举的用表（stacked/expert），枚举不完的用 params_dict 兜底查名字。新模型适配的 一步永远是 print(params_dict.keys()) 对着 checkpoint 名字做 diff。
2. **别名兼容层**（  1 课 `num_experts_per_tok`、  3 课 `mla_use_nope`、本课 mapper）：生态里同一字段有 N 种名字是常态，收口在 config/mapper，不让别名渗进模型代码。
3. **双模型共读一 checkpoint**：主模型 skip_prefixes + MTP 重写函数，配合 `missing_layers` 校验（  8 课 [:343-362](../glm5_next.py#L343-L362)）形成闭环。

2. 10 / 50k / 900k 三个请求，DSA 层与 KDA 层各花多少显存？

   <details><summary>参考答案</summary>

   按 TP=1、BF16 估算（DSA/KDA 配比由 checkpoint `layer_types` 决定，设 D 层 DSA、K 层 KDA）：

   **KDA 层：与长度无关，每请求每层固定 ~2.2 MB**——recurrent_state [64,128,128] ≈ 2 MB（[kimi_kda_state.py:31](../../ops/kimi_kda_state.py#L31)）+ conv_state ≈ 0.14 MB（开 MTP 再加 num_spec 槽）。

   **DSA 层：随长度线性涨，每层 ≈ 1 KB/token + 固定 16 KB**——c_KV 512×2B = 1 KB/token；indexer 压缩 K cache ≈ D_idx/16×2B/token（D_idx=128 时 16 B/token）；压缩尾巴 state cache 为滑动窗 16 token × (k+gate) FP32 ≈ 16 KB/请求固定。

   | 请求长度 | DSA 层/层 | KDA 层/层 |
   |---|---|---|
   | 10 | ~26 KB（尾巴占大头） | ~2.2 MB |
   | 50k | ~50 MB | ~2.2 MB |
   | 900k | **~920 MB** | ~2.2 MB |

   结论：短请求 KDA 的常数反而更贵；长请求 DSA 线性爆炸（×D 层），KDA 纹丝不动——**混合架构 = 把 O(L) 的层压到最少，O(1) 的层扛长度**（第 3/5 课）。

   </details>

3. `model.layers.12.self_attn.indexer.k_cache` 和 `model.layers.12.mlp.experts.w13_weight` 分别是什么、谁管理、形状？

   <details><summary>参考答案</summary>

   **`indexer.k_cache`**：`AscendGlm5NextIndexerKPoolCache` 实例（[:1306-1311](../glm5_next.py#L1306-L1311)，prefix `.indexer.k_cache`）——**cache 张量，不是参数**，`named_parameters()` 里没有它。由引擎 hybrid KV cache manager 按 `get_kv_cache_spec` 声明分页分配，形状 `[num_blocks, block_size, 1, D_idx]` BF16，每 pool 占 1 槽，每步由 `kpool_state_compress_and_write_cache` 融合算子写入，注册进 `static_forward_context` 供 ACLGraph 查找（第 4 课）。**只有 DSA 层才有它**（12 层须是 `deepseek_sparse_attention`）。

   **`experts.w13_weight`**：FusedMoE 把 288 个专家的 gate_proj+up_proj 堆叠成的**真参数**，形状 `[288, 2×2048, 4096]`（约 9.7 GB @BF16；EP=8 时每 rank 36 专家 → ~1.2 GB）。由 vLLM `FusedMoE` 管理排布，加载走 §4 流水线第 7 步 `expert_params_mapping` 带 `expert_id` 写入，TP/EP 切分封装在其 `weight_loader` 里（第 6 课）。

   对照记忆：**cache = 引擎按 spec 分配、随请求增长、无梯度；parameter = 模型自持、checkpoint 按名加载、形状固定**。

   </details>

4. `index_kpool` 从 16 改成 1 会发生什么？

   <details><summary>参考答案</summary>

   KPool 整个机制退化（pool=1 时 softmax 单元素=1，"压缩"变成原样拷贝）：

   1. **indexer cache 显存 ×16**：每 token 独占 1 槽 D_idx，900k 请求从 ~14 MB/层涨回 ~230 MB/层——"16 合 1"白设计。
   2. **Indexer top-k 扫描算力 ×16**（最致命）：打分对象从 L/16 个 pool 变成 L 个 token，1M 上下文下 indexer 自己先撑不住。
   3. **尾巴机制失效**：每 token 立即成池，`always_select_tail` 无尾巴可选，state cache 常空；`ape`（[16, D_idx] 池内位置偏置）失去意义；`topk_width = topk+kpool-1` 缩 15。
   4. 精度上"被选中/落选"的平滑过渡消失，长文检索 recall 的设计缓冲没了。

   功能上仍能跑（全程 config 驱动，第 8 课 MTP 的 `topk_width` 也会跟着变），但把 KPool 存在的两个理由——省 indexer cache、压 indexer 扫描——同时废掉（第 4 课）。

   </details>
